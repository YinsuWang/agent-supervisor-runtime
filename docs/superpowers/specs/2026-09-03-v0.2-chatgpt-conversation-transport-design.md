# V0.2 ChatGPT Conversation Transport Design

Status: **Design draft — Parts I, II and III approved; later sections not yet incorporated**

Date: 2026-09-03

## 1. Goal and scope

V0.2 connects the existing Agent Supervisor Runtime to ChatGPT while preserving the V0.1 architectural boundary: the Orchestrator reasons only in terms of a `SupervisorAdapter`, not browser windows, DOM selectors, cookies, or ChatGPT client internals.

The design supports two primary human-facing ChatGPT surfaces:

- ChatGPT Web in Chrome;
- ChatGPT Desktop.

Both are treated as clients of the same cloud conversation. The runtime communicates through a separate conversation transport layer rather than implementing separate supervisor semantics for each client.

Normal V0.2 operation must not depend on OCR, screenshot recognition, mouse automation, keyboard injection, foreground-window control, or Desktop UI Automation. Those techniques remain fallback-only technologies.

## 2. Approved transport architecture

```text
                    User
                      |
          +-----------+-----------+
          |                       |
          v                       v
   ChatGPT Web                ChatGPT Desktop
      Chrome                     App
          |                       |
          |                 cloud conversation
          |                       ^
          v                       |
+--------------------------------------------+
|        Conversation Transport Layer        |
|                                            |
|  ChromeExtensionTransport                  |
|        OR                                  |
|  BackgroundWebTransport                    |
|        OR                                  |
|  Future FullMcpTransport                   |
|        OR                                  |
|  Future DesktopNativeTransport             |
+-------------------+------------------------+
                    |
                    v
        ChatGPTSupervisorAdapter
                    |
                    v
             V0.1 Orchestrator
                    |
                    v
                   Codex
```

### 2.1 Transport priority

The approved direction is:

1. `ChromeExtensionTransport` — default V0.2 transport for ChatGPT Web users.
2. `BackgroundWebTransport` — compatibility path for users who prefer ChatGPT Desktop while the machine addresses the same cloud conversation through a persistent background browser/WebView profile.
3. `FullMcpTransport` — future capability-dependent transport.
4. `DesktopNativeTransport` — future fallback, UI Automation first and visual/OCR techniques only as a last resort.

### 2.2 New lower-level boundary

The existing `SupervisorAdapter` remains the boundary visible to the Orchestrator. ChatGPT-specific mechanics live below it.

Conceptually:

```ts
interface ConversationTransport {
  connect(binding: ConversationBinding): Promise<void>;
  send(message: TransportMessage): Promise<void>;
  waitForResponse(request: ResponseRequest): Promise<TransportResponse>;
  health(): Promise<TransportHealth>;
  disconnect(): Promise<void>;
}
```

`ChatGPTSupervisorAdapter` translates planning/review operations into machine-readable conversation messages and validates replies. A transport owns only delivery, retrieval, health, and conversation identity.

### 2.3 Chrome mode

```text
Chrome ChatGPT
      |
ASR Chrome Extension
      |
Native Messaging
      |
Local Agent Supervisor Runtime
      |
Codex
```

The extension binds an explicitly selected ChatGPT conversation and communicates with the local runtime through a narrow local channel such as Chrome Native Messaging.

### 2.4 Desktop compatibility

Desktop compatibility is initially provided without controlling the Desktop window:

```text
User -> ChatGPT Desktop
             |
       same cloud conversation
             ^
             |
     Background Web Companion
             |
        Local Runtime
```

The background companion uses a persistent browser/WebView profile. Manual ChatGPT login may be required once during setup; the browser profile may then persist normal session state across process and Windows restarts until the service invalidates the session or the user signs out.

Project/runtime state must not persist ChatGPT passwords, copied session cookies, access tokens, or Desktop credentials.

## 3. Conversation binding

A runtime must never infer that the currently visible ChatGPT conversation is the correct target. Binding is explicit.

A Chrome user binds the current conversation through the ASR extension. The runtime persists ASR-owned binding metadata, conceptually:

```json
{
  "bindingId": "bind_01J...",
  "conversationId": "<chatgpt-conversation-id>",
  "conversationUrl": "https://chatgpt.com/c/<conversation-id>",
  "workspaceId": "ws_01J...",
  "preferredTransport": "chrome-extension",
  "createdAt": "<timestamp>"
}
```

The important distinction is:

```text
workspace
   -> ASR bindingId
      -> external conversationId
```

`bindingId` is the stable ASR identity. `conversationId` identifies the external ChatGPT resource. Rebinding to a new conversation creates a new binding rather than silently mutating the identity of historical machine messages.

Before any send operation, a transport must verify that its current external conversation identity matches the active binding. A mismatch removes send authority.

No credentials belong in `ConversationBinding`.

## 4. Protocol envelope

Every machine-control message exchanged through the conversation carries an explicit protocol envelope. Ordinary user or assistant prose is never interpreted as orchestration state.

Conceptual request envelope:

```text
[ASR/1]
MESSAGE_ID: msg_01J...
BINDING_ID: bind_01J...
TASK_ID: task_01J...
RUN_ID: run_01J...
KIND: REVIEW_REQUEST
SEQUENCE: 7
CORRELATION_ID: msg_01J_previous...
```

The protocol identity fields are:

- `protocolVersion`;
- `messageId`;
- `bindingId`;
- `taskId`;
- `runId`;
- `kind`;
- `sequence`;
- `correlationId` / `inReplyTo`.

A supervisor response must match the expected `bindingId + taskId + runId + inReplyTo` before it is accepted by `ChatGPTSupervisorAdapter` and exposed to the V0.1 Orchestrator.

Free-form wording such as `PASS`, `looks good`, or `revise this` outside a valid protocol response has no machine meaning.

## 5. Durable idempotency and message ledger

V0.2 does not claim theoretical exactly-once browser delivery. Its reliability model is:

> **At-least-once delivery where necessary, combined with durable idempotent processing.**

The runtime maintains a durable message ledger/outbox keyed by `messageId`. A conceptual outbound lifecycle is:

```text
PENDING
  -> CLAIMED
  -> SENT
  -> OBSERVED
  -> RESPONDED
  -> CONSUMED
```

If a transport crashes after sending but before acknowledging success, recovery does not immediately resend. The transport first reconciles the bound conversation and checks whether the same `messageId` is already present. If observed, the ledger advances without re-delivery; only an unobserved message is eligible for retry.

Inbound DOM/browser events are observations, not protocol events. Repeated DOM mutation notifications for the same assistant response are deduplicated by response `messageId`.

`messageId` is the primary idempotency identity. `sequence` is an ordering/checkpoint aid only. A sequence gap triggers reconciliation rather than blind continuation.

## 6. Single-writer transport lease

A binding may have multiple available transports, but at any instant only one transport may have send authority.

The runtime stores a lease conceptually like:

```json
{
  "bindingId": "bind_x",
  "holder": "chrome-extension:instance-A",
  "epoch": 14,
  "expiresAt": "<timestamp>"
}
```

The approved invariant is:

> **One binding has at most one ACTIVE transport at any time.**

### 6.1 TTL and heartbeat

An active transport renews a short TTL lease using heartbeats. If the holder disappears and the lease expires, a standby transport may acquire a new lease.

Example:

```text
Chrome Extension ACTIVE, epoch 14
       |
       X process/browser closes
       |
lease expires
       |
Background Web acquires epoch 15
       |
Background Web ACTIVE
```

### 6.2 Epoch as fencing token

The monotonically increasing `epoch` is mandatory. Every send operation is checked against the current epoch. A previously active transport that later resumes with an old epoch is rejected as stale even if it locally believes it still owns the lease.

This prevents a paused or partitioned transport from becoming a second writer after failover.

### 6.3 Transport states

The transport manager owns its own connectivity states rather than adding browser concepts directly to the V0.1 task state machine:

```text
OFFLINE
STANDBY
ACTIVE
DRAINING
```

A higher-priority transport becoming available does not preempt an in-flight supervisor exchange. Handover occurs at a safe boundary after the current request/response exchange completes. The current holder enters `DRAINING`, finishes the exchange, releases the lease, and the preferred transport then acquires the next epoch.

## 7. Reconciliation before activation

Every reconnect/failover path follows:

```text
connect
  -> RECONCILING
  -> compare durable ledger with observed bound conversation
  -> repair local message state
  -> acquire/validate lease
  -> ACTIVE
```

For example, if durable state says an outbound request is `SENT` while the conversation already contains that request and its correlated assistant response, the runtime advances the local ledger and consumes the existing response instead of sending the request again.

Recovery therefore never treats `transport unavailable` as a reason to re-run Codex. Worker execution state and transport availability remain independent.

## 8. Normal review flow

```text
Codex completes
  -> WorkerResult persisted
  -> RESULT_READY
  -> ChatGPTSupervisorAdapter creates REVIEW_REQUEST
  -> ledger records msg_007 PENDING
  -> Transport Manager selects the ACTIVE lease holder
  -> transport verifies conversationId, bindingId and lease epoch
  -> send msg_007
  -> observe msg_007 in conversation
  -> ChatGPT produces correlated response msg_008
  -> validate bindingId/taskId/runId/inReplyTo/schema
  -> consume msg_008 once
  -> SupervisorAdapter returns Review
  -> V0.1 Orchestrator applies PASS / REVISE / ASK_USER
```

## 9. Interaction with ordinary conversation

A bound ChatGPT conversation remains usable as an ordinary human conversation. The transport consumes only valid ASR protocol envelopes. Other user and assistant messages are ignored by the machine protocol.

This keeps ChatGPT Web/Desktop as the visible human interface rather than turning the conversation into a machine-only console.

## 10. Approved Part II invariants

1. **Explicit binding:** the runtime never guesses the target conversation.
2. **Single writer:** one binding has at most one ACTIVE transport.
3. **Fenced failover:** send authority is protected by a lease epoch.
4. **Durable idempotency:** all machine messages are keyed by `messageId`; recovery reconciles before retrying.
5. **Strict correlation:** a supervisor response must match `bindingId + taskId + runId + inReplyTo` and its schema before reaching the Orchestrator.
6. **Human prose is not protocol:** ordinary conversation cannot accidentally trigger state transitions.
7. **Transport failure is not worker failure:** losing Chrome/Background Web does not imply task loss or blind Codex re-execution.

## 11. Context Broker / MCP-lite data plane

V0.2 separates the small supervisor control plane from local evidence retrieval. The normal review request does not paste full diffs, files, logs, or complete command output into the ChatGPT conversation.

The approved data-flow shape is:

```text
                 ChatGPT Supervisor
                        |
          +-------------+-------------+
          |                           |
      Control Plane               Data Plane
          |                           |
 compact protocol messages       Context Broker
          |                           |
          +-------------+-------------+
                        |
                   Local Runtime
                        |
              Codex / Files / Git
```

### 11.1 Hybrid review packet

Every review begins with a compact evidence packet sufficient for many routine decisions. It should contain small summaries such as:

- task synopsis;
- worker execution summary;
- changed-files summary;
- test summary;
- an evidence manifest describing additional available context.

Large evidence is not attached automatically. Examples include full diffs, full files, long logs and complete stdout/stderr.

A conceptual manifest is:

```json
{
  "runId": "run_07",
  "available": [
    {
      "id": "ctx_diff",
      "type": "git_diff",
      "summary": "4 files changed, +126/-31",
      "size": 11842
    },
    {
      "id": "ctx_tests",
      "type": "test_summary",
      "summary": "38 passed, 0 failed",
      "size": 913
    }
  ]
}
```

The common case remains one supervisor round trip. More expensive evidence is fetched only when the supervisor requests it.

### 11.2 Context Broker boundary

Context retrieval is a separate component rather than browser logic inside `ChatGPTSupervisorAdapter`.

Conceptually:

```ts
interface ContextBroker {
  createManifest(scope: ContextScope): Promise<ContextManifest>;
  fetch(request: ContextRequest): Promise<ContextResponse>;
}
```

The broker owns evidence discovery, read policy, scoping, size limits and auditability. The supervisor adapter only translates protocol requests into broker calls.

### 11.3 Read-only capabilities

The V0.2 broker is an evidence reader, not a second Worker. The initial semantic capability set should remain narrow:

- `execution_summary`;
- `test_summary`;
- `git_status`;
- `git_diff`;
- `changed_files`;
- `read_file`;
- `search_workspace`;
- `list_directory`.

The Context Broker does not expose arbitrary shell execution, writes, commits, network fetches or destructive actions.

### 11.4 Opaque evidence references

Manifest items use ASR-owned opaque references as the preferred access mechanism. The supervisor normally requests:

```json
{
  "ref": "ctx_01JABC"
}
```

rather than constructing arbitrary local paths. Each reference is bound to the relevant workspace/task/run and resolves only through the broker.

This acts as a capability reference and reduces the attack surface of conversation-originated requests.

### 11.5 Controlled dynamic queries

Opaque manifest references are preferred but not sufficient for all reviews. A supervisor may discover that it needs evidence that was not known when the manifest was created.

V0.2 therefore permits a small set of policy-controlled read-only dynamic queries such as workspace search. Dynamic requests are schema validated, workspace scoped and subject to the same evidence budget. They may not be used to construct arbitrary shell commands or unrestricted absolute filesystem reads.

### 11.6 Strict scope and correlation

Every context request is scoped by protocol identity, including:

```text
bindingId
 taskId
 runId
 inReplyTo
```

An evidence reference created for one run must not resolve from another run unless an explicit cross-run evidence type is later designed.

Context request and response messages participate in the same durable message ledger as review messages, for example:

```text
REVIEW_REQUEST msg_7
  -> CONTEXT_REQUEST msg_8
  -> CONTEXT_RESPONSE msg_9
  -> REVIEW msg_10
```

This lets reconciliation recover an interrupted evidence exchange without restarting the review or re-running Codex.

### 11.7 Bounded large-content delivery

Large evidence may be truncated and continued through opaque continuation tokens. Continuations are broker-issued, run scoped and expiring; the supervisor does not control arbitrary byte offsets or filesystem paths.

The broker enforces both per-response and per-review-cycle evidence budgets. Exact byte defaults remain implementation-tunable and should be selected through benchmarks, but unbounded evidence transfer is explicitly prohibited.

If a budget is exhausted, the protocol returns a structured budget condition so the supervisor can narrow its query or ask the user rather than silently dumping more context.

### 11.8 One semantic API for conversation and MCP

Conversation-based MCP-lite and future Full MCP must share the same `ContextBroker` semantic capabilities.

```text
               ContextBroker
                     |
            semantic capabilities
                     |
         +-----------+-----------+
         |                       |
         v                       v
ConversationContextAdapter    MCP Adapter
browser/Plus path             future supported path
```

The browser path serializes a context request into the ASR conversation protocol. A future MCP adapter may expose the same operation as an MCP tool. Both resolve through the same broker implementation, policies and evidence schemas.

Upgrading transport therefore must not require a second data-plane implementation or changes to the Orchestrator.

## 12. Approved Part III invariants

1. **Compact by default:** review requests carry summaries and an evidence manifest, not full diffs/logs by default.
2. **Fetch on demand:** the supervisor obtains additional evidence through the Context Broker only when needed.
3. **Opaque refs first:** evidence access prefers ASR-owned capability references; dynamic queries are narrow and policy controlled.
4. **Read only:** the Context Broker cannot execute or modify the task environment.
5. **Strict scope:** all context access is bound to `bindingId + taskId + runId` and recorded in the durable protocol/audit trail.
6. **Bounded transfer:** per-response and per-review-cycle evidence budgets are mandatory.
7. **One semantic layer:** conversation MCP-lite and future Full MCP adapters share the same Context Broker API and evidence model.

## 13. Design status

Parts I, II and III of this document are approved. The following architectural areas will be designed separately and incorporated only after approval:

- exact extension/runtime wire protocol and Native Messaging host lifecycle;
- background browser implementation choice;
- security and permission model;
- transport outage/state integration details;
- testing and V0.2 acceptance criteria.
