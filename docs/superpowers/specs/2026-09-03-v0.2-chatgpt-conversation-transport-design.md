# V0.2 ChatGPT Conversation Transport Design

Status: **Approved**

Date: 2026-09-03

## 1. Goal and scope

V0.2 connects the existing Agent Supervisor Runtime (ASR) to ordinary ChatGPT conversations while preserving the V0.1 architectural boundary: the Orchestrator reasons only in terms of supervisor and worker contracts. Browser windows, DOM selectors, authentication cookies, native messaging, and ChatGPT client details remain below the supervisor boundary.

The target user experience is:

1. The user works in an ordinary ChatGPT conversation, in ChatGPT Web/Chrome or ChatGPT Desktop.
2. ChatGPT acts as Planner, Supervisor, and Reviewer.
3. ASR durably dispatches local work to Codex.
4. Codex executes locally and produces machine-observed evidence.
5. ChatGPT receives a compact review packet and may request additional read-only evidence.
6. ChatGPT returns `PASS`, `REVISE`, or `ASK_USER` through a validated machine protocol.
7. `REVISE` automatically redispatches work; `ASK_USER` and policy boundaries are the normal reasons to interrupt the user.
8. Closing Chrome, closing a transport process, or restarting Windows must not cause blind Codex re-execution or task loss.

V0.2 is single-machine-first, Windows-first, TypeScript-first, and must not require a public domain, tunnel, second physical PC, database server, or Full MCP capability.

Normal V0.2 operation must not depend on OCR, screenshot recognition, mouse coordinates, physical keyboard injection, foreground-window ownership, or ChatGPT Desktop UI Automation. Such technologies are not part of the normal V0.2 path.

## 2. Architectural overview

```text
                               User
                                |
                   +------------+------------+
                   |                         |
                   v                         v
              ChatGPT Web              ChatGPT Desktop
                 Chrome                      App
                   |                         |
                   |                   same cloud chat
                   |                         ^
                   v                         |
           Chrome Extension          Background Web
           + Content Script           Companion
                   |                         |
                   +------------+------------+
                                |
                       ConversationTransport
                                |
                         Transport Manager
                Binding / Lease / Reconciliation
                                |
               +----------------+----------------+
               |                                 |
               v                                 v
     ChatGPTSupervisorAdapter              Context Broker
               |                                 |
               |                         Git / Files / Tests
               |                         Runtime Evidence
               |
               v
                          Orchestrator
                 State / Policy / Recovery
                     Revision / Retry
                                |
                                v
                          WorkerAdapter
                                |
                       CodexExecWorker V0.1
                                |
                    CodexAppServerWorker future
```

The guiding principle remains:

> The Orchestrator knows neither ChatGPT client internals nor Codex client internals. It knows supervisor and worker contracts.

V0.2 therefore adds a lower-level conversation transport boundary beneath `ChatGPTSupervisorAdapter`.

Conceptually:

```ts
interface ConversationTransport {
  connect(binding: ConversationBinding): Promise<void>;
  send(message: TransportMessage): Promise<void>;
  waitForResponse(request: ResponseRequest): Promise<TransportResponse>;
  health(): Promise<TransportHealth>;
  disconnect(): Promise<void>;
}
```

`ChatGPTSupervisorAdapter` owns supervisor semantics and response validation. A conversation transport owns delivery, observation, conversation identity, connectivity, and transport-specific reconciliation.

## 3. Transport strategy

### 3.1 Transport priority

The approved direction is:

1. `ChromeExtensionTransport` — default V0.2 transport when the user works in ChatGPT Web.
2. `BackgroundWebTransport` — compatibility transport when the user prefers ChatGPT Desktop, operating the same cloud conversation through a persistent background web session.
3. `FullMcpTransport` — future capability-dependent transport using the same semantic Context Broker.
4. `DesktopNativeTransport` — future fallback only; it is not part of the normal V0.2 implementation path.

Chrome and Desktop are different clients of one ChatGPT cloud conversation, not different supervisors. The durable anchor is the bound conversation, not a specific UI process.

### 3.2 Chrome path

```text
ChatGPT page
    |
Content Script
    |
MV3 Extension Service Worker
    |
Chrome Native Messaging
    |
Thin ASR Native Host
    |
Windows Named Pipe
    |
ASR Runtime Daemon
```

The content script handles ChatGPT page semantics. The MV3 service worker owns extension/native messaging coordination. The native host is a thin bridge. Durable state remains in the ASR Runtime.

### 3.3 Desktop compatibility path

```text
User -> ChatGPT Desktop
             |
       same cloud conversation
             ^
             |
     Background Web Companion
     Playwright persistent profile
             |
        ASR Runtime
```

The Desktop window is not controlled. The background companion accesses the same conversation using a dedicated persistent browser profile.

## 4. Conversation binding

A runtime must never infer that whichever ChatGPT conversation is currently visible is the correct target. Binding is explicit.

A binding is ASR-owned metadata, conceptually:

```json
{
  "bindingId": "bind_01J...",
  "conversationId": "<chatgpt-conversation-id>",
  "conversationUrl": "https://chatgpt.com/c/<conversation-id>",
  "workspaceId": "ws_01J...",
  "preferredTransport": "chrome-extension",
  "createdAt": "<timestamp>"
}
```

Identity is layered:

```text
workspace
   -> ASR bindingId
      -> external conversationId
```

`bindingId` is the durable ASR identity. `conversationId` identifies the external ChatGPT resource. Rebinding creates a new binding. Historical messages keep their original binding identity.

Before any send operation, the active transport must verify that its observed external conversation identity matches the active binding. A mismatch removes send authority.

No passwords, cookies, access tokens, refresh tokens, copied session headers, or Desktop credentials belong in `ConversationBinding` or `.orchestrator/` state.

V0.2 supports many historical bindings but one active binding per workspace. A binding permits at most one active machine exchange at a time.

## 5. Conversation protocol envelope

Every ASR machine-control message carried through a normal ChatGPT conversation contains an explicit protocol envelope. Ordinary user or assistant prose has no machine meaning.

Conceptual envelope:

```text
[ASR/1]
MESSAGE_ID: msg_01J...
BINDING_ID: bind_01J...
TASK_ID: task_01J...
RUN_ID: run_01J...
KIND: REVIEW_REQUEST
SEQUENCE: 7
CORRELATION_ID: msg_previous...
```

Required semantic identity fields are:

- `protocolVersion`;
- `messageId`;
- `bindingId`;
- `taskId`;
- `runId`;
- `kind`;
- `sequence`;
- `correlationId` / `inReplyTo`.

A supervisor response is accepted only when `bindingId + taskId + runId + inReplyTo` match the pending exchange and the response schema validates. Free-form text such as `PASS` or `looks good` outside a valid protocol response cannot transition task state.

The conversation protocol is separate from browser/native IPC. `ASR/1` describes supervisor semantics; the browser bridge uses a distinct `ASR-NM/1` protocol.

## 6. Durable message ledger and idempotency

V0.2 does not claim theoretical exactly-once delivery through browser automation. Its reliability model is:

> At-least-once delivery where necessary, combined with durable idempotent processing.

The runtime maintains a durable message ledger keyed by `messageId`. A conceptual outbound lifecycle is:

```text
PENDING
  -> CLAIMED
  -> SENT
  -> OBSERVED
  -> RESPONDED
  -> CONSUMED
```

A transport crash after submission but before acknowledgement does not cause immediate resend. Recovery first reconciles the bound conversation and checks whether the same `messageId` is already observable. Existing requests or responses advance local ledger state without re-delivery.

Browser DOM mutation events are observations, not protocol events. Duplicate DOM events for one assistant response are deduplicated by message identity.

`messageId` is the primary idempotency key. `sequence` is an ordering/checkpoint aid. A sequence gap triggers reconciliation rather than blind continuation.

All review, context request, context response, and final review messages participate in the same durable ledger.

## 7. Single-writer transport lease

Multiple transports may be available for one binding, but only one may send at any instant.

Conceptual lease:

```json
{
  "bindingId": "bind_x",
  "holder": "chrome-extension:instance-A",
  "epoch": 14,
  "expiresAt": "<timestamp>"
}
```

Invariant:

> One binding has at most one ACTIVE transport at any time.

The holder renews a short TTL lease using heartbeats. If the holder disappears, a standby transport may acquire the lease after expiry.

The monotonically increasing `epoch` is a fencing token. Every send is checked against the current epoch. A resumed stale transport is rejected even if it locally believes that it still owns the lease.

Transport manager connectivity states are:

```text
OFFLINE
STANDBY
ACTIVE
DRAINING
```

Higher-priority transports do not preempt an in-flight supervisor exchange. Handover occurs at a safe exchange boundary: the current holder drains the request/response turn, releases its lease, and the preferred transport acquires the next epoch.

## 8. Reconciliation and recovery

Every reconnect/failover follows:

```text
connect
  -> RECONCILING
  -> compare durable ledger with observed bound conversation
  -> repair local message state
  -> acquire/validate lease
  -> ACTIVE or STANDBY
```

If durable state says a review request is `SENT` but the conversation already contains both that request and a correlated assistant response, recovery advances local state and consumes the existing response. It does not send a duplicate request.

Worker execution and supervisor connectivity are independent. Losing Chrome, a background browser, a native host, or a ChatGPT session does not imply Codex failure and never justifies blind worker re-execution.

## 9. Context Broker / MCP-lite data plane

V0.2 separates the compact supervisor control plane from a read-only evidence data plane.

```text
                 ChatGPT Supervisor
                        |
          +-------------+-------------+
          |                           |
      Control Plane               Data Plane
          |                           |
   ASR/1 messages               Context Broker
          |                           |
          +-------------+-------------+
                        |
                   Local Runtime
```

### 9.1 Compact review packet

A normal review request contains a small default packet:

- task synopsis;
- worker execution summary;
- changed-files summary;
- test summary;
- evidence manifest.

It does not automatically embed full diffs, full files, full logs, or complete stdout/stderr.

### 9.2 Evidence manifest

The Context Broker creates a run-scoped manifest containing opaque evidence references, type, compact summary, and size metadata. Example:

```json
{
  "runId": "run_07",
  "available": [
    {
      "id": "ctx_diff",
      "type": "git_diff",
      "summary": "4 files changed, +126/-31",
      "size": 11842
    },
    {
      "id": "ctx_tests",
      "type": "test_summary",
      "summary": "38 passed, 0 failed",
      "size": 913
    }
  ]
}
```

The Supervisor can request an opaque `ref` rather than constructing arbitrary filesystem paths.

### 9.3 Capabilities

Initial V0.2 read-only capabilities are limited to:

- `execution_summary`;
- `test_summary`;
- `git_status`;
- `git_diff`;
- `changed_files`;
- `read_file`;
- `search_workspace`;
- `list_directory`.

The Context Broker does not expose arbitrary shell execution, arbitrary process execution, file writes, `git commit`, or general network fetch.

Opaque refs are preferred. Controlled dynamic queries are allowed only through a strict read-only policy and workspace boundary validation.

Every request is scoped to `bindingId`, `taskId`, and `runId`. Evidence created for another run is rejected.

Large responses use opaque continuation tokens with run scope and expiry. The Supervisor cannot select arbitrary byte offsets or bypass evidence policy.

The Context Broker enforces per-response and per-review-cycle budgets. Exact default byte values may be tuned during implementation, but the existence of both limits is required.

### 9.4 MCP compatibility

Conversation MCP-lite and future Full MCP must share one internal semantic `ContextBroker` API. Full MCP is an alternate adapter to the same evidence capabilities, not a second data plane implementation.

## 10. Native Messaging, runtime IPC, and process lifecycle

### 10.1 Responsibility boundary

```text
Extension
= web/client adapter

Native Host
= thin IPC bridge

ASR Runtime
= durable authority
```

The native host does not own tasks, worker runs, review policy, leases, message ledger state, Context Broker semantics, or Codex execution.

### 10.2 Long-lived Native Messaging port

The extension uses Chrome `runtime.connectNative()` for a bidirectional connection rather than spawning a fresh native host per message with `sendNativeMessage()`.

The native host communicates with Chrome through the documented Native Messaging stdin/stdout length-prefixed UTF-8 JSON protocol. Debug output goes to stderr only.

### 10.3 ASR-NM/1 transport protocol

The local bridge uses a separate protocol from the ChatGPT conversation protocol. Top-level frame classes are intentionally small:

```text
HELLO
WELCOME
COMMAND
EVENT
ACK
ERROR
HEARTBEAT
```

Conceptual frame:

```json
{
  "protocol": "ASR-NM/1",
  "frameId": "frame_01J...",
  "type": "COMMAND",
  "sessionId": "session_x",
  "timestamp": "<timestamp>",
  "payload": {
    "name": "SEND_CONVERSATION_MESSAGE"
  }
}
```

`ACK` means only that the IPC frame was accepted for processing. It does not mean that ChatGPT received a message or completed a response. External lifecycle is reported through explicit events such as message submitted, message observed, response started, and response completed.

### 10.4 HELLO/WELCOME negotiation

Every new extension/native/runtime session performs protocol and capability negotiation before any conversation command is accepted.

The extension has a durable per-install/profile `extensionInstanceId`, distinct from the Chrome extension ID. The runtime returns `runtimeInstanceId` and a fresh connection `sessionId`.

Incompatible protocol versions fail closed with `PROTOCOL_INCOMPATIBLE`.

### 10.5 Runtime daemon

ASR Runtime is an independent per-OS-user authority daemon. It may manage multiple workspaces and bindings.

Default behavior is lazy auto-start. When a native host cannot connect to the runtime, it may start the daemon and wait for readiness. A single-instance lock or OS-level mutex prevents duplicate runtime authorities.

Optional user-level login startup is exposed separately, conceptually through:

```text
orchestrator service enable
orchestrator service disable
```

V0.2 must not require administrator privileges for the normal per-user installation path.

### 10.6 Host-to-runtime IPC

Windows V0.2 uses a per-user Named Pipe. The IPC abstraction must permit future Unix Domain Socket support without changing higher-level protocols.

The normal implementation does not expose a localhost HTTP/WebSocket server for browser transport.

### 10.7 Native host registration

Windows Native Messaging registration uses the current-user registry (`HKCU`) and an exact `allowed_origins` Chrome extension origin. Wildcard origins are forbidden.

Setup/uninstall commands create and remove only ASR-owned host manifests and registry entries.

## 11. Background Web Companion

V0.2 uses Playwright with a dedicated persistent Chromium user-data directory for Desktop compatibility.

The companion profile is separate from the user’s normal Chrome profile. The user may perform a one-time manual ChatGPT login through a visible companion-login flow. Browser-managed session state persists inside that dedicated profile until ChatGPT invalidates it or the user signs out.

ASR does not copy, export, parse, or store ChatGPT cookies or authentication tokens in project/runtime state.

Conceptual commands:

```text
orchestrator companion login
orchestrator companion reset
```

If authentication expires, the Supervisor connectivity state becomes `AUTH_REQUIRED`. Task state is preserved.

The companion is a standby transport when a higher-priority Chrome extension transport is active. The Part II lease and drain rules control automatic failover and safe handback.

## 12. ChatGPT Page Driver and DOM compatibility

Browser-specific page automation is isolated behind a semantic page-driver contract, conceptually:

```ts
interface ChatGptPageDriver {
  inspectConversation(): Promise<ConversationIdentity>;
  submitMessage(message: string): Promise<SubmitReceipt>;
  observeMessages(cursor?: MessageCursor): AsyncIterable<PageMessage>;
  detectGenerationState(): Promise<GenerationState>;
  health(): Promise<PageCompatibility>;
}
```

Chrome extension and Playwright backends share the same semantic model and compatibility rules while using different low-level DOM access mechanisms.

### 12.1 Selector policy

Priority order is:

1. semantic HTML structure;
2. ARIA roles and accessible names;
3. stable attributes and relative document relationships;
4. compatibility-profile-specific selectors only when necessary.

Brittle CSS-class/coordinate chains are not an architectural dependency.

### 12.2 Composer interaction

The page driver uses DOM/browser editing semantics and web input events needed by the page’s editor model. It does not require Win32 `SendKeys`, physical mouse coordinates, foreground focus, or OCR.

### 12.3 Response lifecycle

The driver does not use fixed sleep durations to infer completion. It combines semantic message-node observation, generation controls/state, and a content-stability condition to emit response lifecycle events.

All observations still correlate to ASR protocol message identities; DOM events alone cannot transition orchestration state.

### 12.4 Compatibility probe

Every transport activation performs a non-destructive compatibility probe covering at least:

- conversation identity detection;
- composer detection/writability;
- submit capability;
- user-message observation;
- assistant-message observation;
- streaming/generation lifecycle detection.

If required capabilities are not available, the transport becomes `INCOMPATIBLE` and fails closed. It must not fall back to random clicking, OCR, or guessing.

### 12.5 Mandatory feasibility gate

Before production browser integration proceeds, implementation must run a focused real-ChatGPT feasibility spike validating:

1. conversation identity can be identified;
2. the extension can semantically submit a test message;
3. a background tab can support the required observation/send flow;
4. streaming completion can be detected;
5. the correlated assistant response can be read;
6. a Playwright persistent profile can reuse a manual ChatGPT login;
7. the same cloud conversation can be observed by Desktop while the companion accesses it through Web.

If the spike fails materially, production browser implementation stops and the transport architecture is reassessed. OCR is not the automatic fallback.

## 13. Security and trust boundaries

ChatGPT/web content is external input, not trusted local code.

```text
ChatGPT / Web content
        |
      untrusted
        |
        v
Supervisor Protocol Validator
        |
        v
Policy Engine
        |
        v
Local Runtime
        |
        v
Codex Worker
```

There is no direct path from browser content to arbitrary shell execution.

The only local execution path is:

```text
validated supervisor semantics
        -> Orchestrator
        -> policy
        -> WorkerTask
        -> WorkerAdapter / Codex
```

Context Broker remains read-only and workspace-scoped.

Chrome extension permissions are minimized to the ChatGPT origins and required extension APIs. Native Messaging uses an exact allowed extension ID. Named Pipe access is restricted to the current OS user.

Path-based Context Broker requests resolve canonical paths and must remain inside configured allowed workspace roots. Sensitive unrelated locations such as SSH credentials, browser profiles, and credential stores are not exposed through Context Broker.

The browser/native channel exposes only narrow transport operations. It must not expose `run_shell`, arbitrary filesystem read, direct Codex execution, or equivalent general local-RCE primitives.

## 14. Failure model and state integration

V0.2 keeps task lifecycle and supervisor connectivity orthogonal.

V0.1 task state remains authoritative for work semantics. V0.2 introduces a separate supervisor/session state:

```text
OFFLINE
CONNECTING
AUTH_REQUIRED
RECONCILING
STANDBY
ACTIVE
DEGRADED
INCOMPATIBLE
```

Examples:

| Event | Task state effect | Supervisor/transport behavior |
| --- | --- | --- |
| Chrome closes | unchanged | OFFLINE; companion may acquire lease |
| Native Host crashes | unchanged | reconnect/recreate host |
| Runtime restarts | recover durable task state | RECONCILING |
| ChatGPT login expires | unchanged | AUTH_REQUIRED |
| ChatGPT DOM compatibility breaks | unchanged | INCOMPATIBLE; stop automation |
| Background browser crashes | unchanged | restart/reconcile or wait |
| Message delivery is uncertain | unchanged | reconcile ledger/conversation before retry |
| Codex technical failure | V0.1 retry/failure policy | transport unrelated |
| Invalid supervisor schema | V0.1 `BLOCKED` policy | transport may remain ACTIVE |
| Lease holder disappears | unchanged | failover to new epoch |

Transport unavailability by itself is not `FAILED` and not a reason for `BLOCKED`.

V0.1 `BLOCKED` remains reserved for user judgment, invalid supervisor semantics, safety/scope boundaries, repeated unresolved findings, or exhausted substantive revision policy.

## 15. Human interaction and concurrency

A bound conversation remains an ordinary ChatGPT conversation. The machine parser consumes only valid ASR protocol envelopes. Ordinary human messages are ignored by the machine protocol.

A human message inserted while a machine review is pending does not become a Worker instruction automatically. Any substantive new work must return through validated supervisor semantics, for example a new task or `REVISE` decision.

V0.2 concurrency is deliberately conservative:

- one runtime may manage multiple workspaces and bindings;
- one binding permits at most one active machine supervisor exchange;
- one workspace has one active binding at a time;
- historical tasks and retired bindings remain readable;
- parallel multi-worker orchestration is deferred beyond V0.2.

## 16. Packaging and installation UX

The normal user must not manually edit the Windows registry or hand-author native host manifests.

Primary guided entry point:

```text
orchestrator setup
```

The setup flow checks the environment, Codex availability, runtime home, Native Messaging host registration, extension connectivity, companion profile readiness, and overall doctor status.

Advanced lifecycle commands may include:

```text
orchestrator daemon
orchestrator service enable
orchestrator service disable
orchestrator browser install
orchestrator browser uninstall
orchestrator companion login
orchestrator companion reset
orchestrator bind
orchestrator unbind
orchestrator doctor
```

Windows 10/11 and PowerShell 7 are first-class V0.2 targets, subject to dependency support floors. macOS/Linux IPC and installer backends may be added later without changing higher-level contracts.

Normal setup is per-user and should not require elevation.

## 17. Testing strategy

Real ChatGPT is not a mandatory PR-CI dependency.

The testing pyramid is:

1. unit tests for protocols, schemas, binding, ledger, lease/fencing, Context Broker policies, budgets, continuation tokens, state mapping, and version negotiation;
2. integration tests for runtime/native host IPC, Named Pipe behavior, daemon auto-start, recovery, failover, and Context Broker evidence sources;
3. browser integration tests against a deterministic `FakeChatGPTPage` fixture implementing composer, conversation identity, streaming, message history, DOM mutation, and failure modes;
4. manual-gated real ChatGPT compatibility smoke tests.

The CI suite must remain runnable without ChatGPT credentials, cookies, 2FA, or private tokens.

A compatibility doctor command should surface semantic capability results instead of silently falling back when the live ChatGPT page changes.

Known-red TDD work should be kept off shared PR branches where practical so expected development failures do not generate unnecessary CI notification noise.

## 18. V0.2 acceptance criteria

V0.2 is releasable only when the following end-to-end flow works:

```text
User in ordinary ChatGPT conversation
        -> bind once
        -> create/delegate task
        -> Codex executes automatically
        -> result persists
        -> ChatGPT receives compact review packet
        -> optionally requests Context Broker evidence
        -> PASS / REVISE / ASK_USER
        -> REVISE automatically dispatches Codex again
        -> PASS completes the task
```

Recovery and safety acceptance criteria additionally require:

- Chrome close/reopen does not lose or duplicate work;
- Windows/runtime restart restores durable work without blind worker rerun;
- duplicate transport/DOM observations do not duplicate processing;
- Chrome/Background transport failover obeys the lease epoch;
- ChatGPT login expiry preserves task state;
- a wrong conversation cannot receive a bound machine message;
- a stale transport cannot send after lease loss;
- ordinary human chat cannot accidentally transition task state;
- Context Broker cannot execute arbitrary shell or escape allowed workspace roots;
- incompatible ChatGPT DOM behavior fails closed;
- no ChatGPT credentials are persisted in project/runtime task state.

## 19. Implementation milestones and gate

Implementation should proceed as independently testable milestones:

1. **M1 — Conversation reliability core:** Binding, `ASR/1`, Message Ledger, Lease/fencing, reconciliation primitives.
2. **M2 — Context Broker:** compact review packet, manifests, read-only evidence capabilities, budgets, continuation.
3. **M3 — Local transport runtime:** daemon, Named Pipe IPC, Native Messaging host, `ASR-NM/1`, auto-start and version negotiation.
4. **M4 — Chrome Extension shell:** MV3 extension, binding UX, service-worker/native bridge, transport registration.
5. **M5 — Browser feasibility gate and production page driver:** real ChatGPT spike first, then production DOM adapter only if the gate passes.
6. **M6 — Background Web Companion:** Playwright persistent profile, manual login flow, Desktop-compatible same-conversation operation.
7. **M7 — Recovery, installer, doctor, security hardening:** failover/handover, setup/uninstall, state reporting, permissions, policy hardening.
8. **M8 — E2E, Windows verification, documentation, V0.2 release readiness.**

M5 is a hard architecture gate. A material feasibility failure stops production browser integration and triggers design reassessment instead of an automatic OCR/UI-automation workaround.

## 20. Explicit V0.2 non-goals

V0.2 does not include:

- parallel multi-worker orchestration;
- cloud-hosted ASR service;
- mandatory second-PC execution;
- arbitrary remote desktop/access functionality;
- ChatGPT Desktop UI Automation as a normal transport;
- OCR or screenshot recognition as a normal transport;
- private ChatGPT API reverse engineering;
- extraction or copying of ChatGPT authentication tokens/cookies;
- Full MCP as a requirement;
- a database server;
- a web dashboard;
- mandatory public tunnels or domains.

Future adapters may include a Full MCP conversation/data-plane adapter, a Desktop-native fallback, Unix local IPC, and a persistent `CodexAppServerWorker` without changing the core Orchestrator contracts.

## 21. Approved invariants

1. The V0.1 Orchestrator does not know browser or ChatGPT-client internals.
2. Conversation identity is explicit and durable through `bindingId`.
3. One binding has at most one ACTIVE sending transport.
4. Lease epoch is a mandatory fencing token for send authority.
5. Machine messages are durably idempotent by `messageId`; reconnect reconciles before retry.
6. Supervisor responses must match `bindingId + taskId + runId + inReplyTo` and schema.
7. Ordinary human prose has no machine protocol meaning.
8. Transport failure is not worker failure.
9. Context Broker is bounded, read-only, run-scoped, and auditable.
10. MCP-lite and future Full MCP share one Context Broker semantic API.
11. ASR Runtime is the durable authority; Native Host is a thin bridge.
12. Extension/service-worker/native-host processes may disappear without losing core task state.
13. Browser/native channels expose no arbitrary shell or unrestricted local filesystem capability.
14. ChatGPT authentication remains browser-managed and is not copied into ASR project/task state.
15. ChatGPT page incompatibility fails closed.
16. The M5 real-page feasibility spike is mandatory before production browser integration is considered complete.
