# V0.2 Conversation Transport Direction

Status: **Approved architecture direction; not the complete V0.2 specification**

Date: 2026-09-03

## Purpose

V0.2 will connect the existing supervisor runtime to ChatGPT without making desktop-window recognition the primary transport. The approved direction is to separate the reasoning role (`ChatGPTSupervisorAdapter`) from the mechanism used to reach a ChatGPT conversation (`ConversationTransport`).

The user-facing surface may be either ChatGPT Web in Chrome or ChatGPT Desktop. The runtime should treat both as clients of the same cloud conversation rather than as separate supervisor implementations.

## Core decision

V0.2 adopts the following transport priority:

1. **Chrome Extension transport** — default for users who use ChatGPT Web.
2. **Background Web Companion transport** — compatibility path for users who prefer ChatGPT Desktop while the machine communicates with the same cloud conversation through a persistent background web profile.
3. **Full MCP transport** — future transport when the connected ChatGPT plan/environment supports the required MCP actions.
4. **Desktop native transport** — future fallback using UI Automation first and visual/OCR techniques only as a last resort.

OCR, screenshot recognition, mouse automation, keyboard injection, and foreground-window control are explicitly **not** part of the normal V0.2 path.

## New boundary

The existing `SupervisorAdapter` remains the reasoning/runtime boundary. V0.2 introduces a lower-level transport abstraction so ChatGPT-specific conversation mechanics do not leak into the Orchestrator.

Conceptually:

```ts
interface ConversationTransport {
  connect(binding: ConversationBinding): Promise<void>;
  send(message: TransportMessage): Promise<void>;
  waitForResponse(request: ResponseRequest): Promise<TransportResponse>;
  health(): Promise<TransportHealth>;
  disconnect(): Promise<void>;
}
```

`ChatGPTSupervisorAdapter` will translate planning/review requests into conversation messages and parse validated supervisor responses. The transport only owns delivery, response retrieval, connection health, and conversation identity.

## Chrome-integrated mode

The default V0.2 UX is ChatGPT Web in Chrome with a small ASR extension.

```text
Chrome ChatGPT
      |
ASR Chrome Extension
      |
Native Messaging
      |
Local Agent Supervisor Runtime
      |
Codex
```

This path should not require OCR, UI Automation, remote-debugging ports, mouse movement, or keyboard simulation. The extension is expected to bind one explicit ChatGPT conversation and communicate with the local runtime through Chrome Native Messaging or an equivalent narrow local channel.

## ChatGPT Desktop compatibility

Desktop compatibility should not initially be implemented by controlling the Desktop window.

Instead:

```text
User -> ChatGPT Desktop
             |
       same cloud conversation
             ^
             |
     Background Web Companion
             |
        Local Runtime
```

A persistent background browser/WebView profile may be logged in manually once during setup and then reused across browser, Codex, and Windows restarts until the ChatGPT session itself expires or the user signs out. The runtime stores only conversation binding metadata; it must not copy or persist ChatGPT passwords, session tokens, cookies, or Desktop credentials in project state.

The machine-side companion opens the same conversation URL/ID used by the Desktop client. Therefore the user may interact through Desktop while ASR communicates through web DOM/browser primitives in the background.

## Conversation identity is the stable anchor

The runtime should not care whether the human currently views the conversation in Chrome or Desktop. It should persist a binding such as:

```json
{
  "supervisor": {
    "type": "chatgpt",
    "conversation": {
      "id": "<conversation-id>",
      "url": "https://chatgpt.com/c/<conversation-id>",
      "preferredTransport": "chrome-extension"
    }
  }
}
```

No credentials belong in this binding.

A future transport manager may prefer the Chrome extension when it is available and fall back to the background web companion when it is not, without changing the task or supervisor state.

## Recovery intent

Transport availability must be separate from task execution state. Closing Chrome, closing Codex, or rebooting Windows must not imply task loss or blind re-execution.

The intended behavior is:

```text
transport unavailable
        |
        v
supervisor temporarily unavailable
        |
        v
retain durable V0.1 state
        |
transport reconnects
        |
        v
resume from persisted RESULT_READY / REVIEWING / blocked state
```

The exact V0.2 state representation for transport outages is still to be designed. This document intentionally does not freeze that detail.

## Relationship to reference projects

The direction deliberately incorporates architectural lessons already demonstrated by related community projects:

- `XiaoDuoYa/codex-with-chatgpt`: separate a tiny control plane from a context/data plane; avoid shipping large diffs and logs through every control message.
- `Zhenyu98/codex-chatgpt-bridge`: treat ChatGPT as architect/reviewer and Codex as executor/verifier using compact task packets and structured handoffs.
- `joseanu/codex-from-chatgpt`: expose Codex through a compact job-oriented interface and prefer persistent Codex threads when available.
- `Dazlarus/chatgpt-escalation-mcp`: retain desktop UI automation only as a compatibility/fallback lesson, not as the primary V0.2 architecture.

V0.1 remains responsible for durable state, retry/revision policy, crash recovery, worker evidence, and the core supervisor-worker loop.

## Explicit non-goals for this architecture direction

This document does **not** yet specify:

- the extension-to-runtime wire protocol;
- Native Messaging host installation details;
- DOM selectors or page integration mechanics;
- exact conversation binding/verification handshake;
- duplicate-message prevention;
- multi-tab or multi-conversation arbitration;
- background companion browser technology choice;
- transport failover timing;
- transport outage state-machine additions;
- context-broker / MCP-lite protocol;
- security policy for extension permissions;
- V0.2 tests and acceptance criteria.

Those items must be designed and approved before the formal V0.2 spec and implementation plan are written.

## Approved principle

> **Chrome Extension is the default V0.2 conversation transport. ChatGPT Desktop is supported through a Background Web Companion that addresses the same cloud conversation. Desktop UI Automation and OCR are fallback technologies, not the normal communication path.**
